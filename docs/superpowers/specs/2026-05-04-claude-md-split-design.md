# 设计规格：CLAUDE.md 拆分重构

## 1. 背景与目标

当前 `CLAUDE.md` 约 400 行,包含高频硬规则与大量低频细则。由于 Claude Code 每次执行代码相关任务前都需读取 `CLAUDE.md`,全文加载会带入大量不相关的低频规则上下文。

**目标**：
- 将 `CLAUDE.md` 压缩为高频硬规则主入口(约 100 行以内)
- 将低频细则拆分到 `docs/meta/` 下的独立规则文件
- 不改变任何规则含义
- 主入口保留按需读取细则文件的索引

## 2. 拆分原则

1. **不改变规则含义**：所有细则原文迁移,不增删改规则条款
2. **按场景聚类**：将相关主题归入同一文件,避免文件过多
3. **主入口保留索引**：`CLAUDE.md` 通过索引列表指向各细则文件,并注明读取时机
4. **文件命名统一**：以 `claude_` 前缀标识 Claude Code 专用规则,以主题后缀标识内容范畴

## 3. 新文件结构

```
/CLAUDE.md                              # 高频硬规则主入口
/docs/meta/
  docs_framework_overview.md            # (已有)文档体系总纲
  collaboration_workflow_guide.md       # (已有)协作动作说明
  claude_execution_workflows.md         # (新建)执行流程细则
  claude_doc_permissions.md             # (新建)文档权限细则
  claude_code_style_guide.md            # (新建)代码规范细则
  claude_reporting_guide.md             # (新建)汇报与停止细则
```

- 5.2 必须由 yiyi 明确触发的动作清单
- 5.3 可自动衍生执行的动作清单与前提条件
- 9.1 阶段执行规则
- 9.2 Bug 修复规则
- 9.3 需求补充(并入)规则
- 9.4 阶段收尾/交接规则
- 9.5 业务需求完成判定
- 9.6 阶段功能完成判定
- 9.7 提交后优化规则

**读取时机**：当任务涉及阶段执行、Bug 修复、需求并入或阶段收尾时,按需读取。

### 4.2 `docs/meta/claude_doc_permissions.md`

**来源**：`CLAUDE.md` 第 6 节(文档权限与更新规则)

**内容**：
- 自动可改文档清单(`/TODO.md`、`/docs/testing/stage_XX_manual_test.md`)
- 询问后可改文档清单
- 只读文档清单

- 修改边界规则(不得静默修改阶段范围、验收边界等)

**读取时机**：当任务涉及文档更新、归档或权限边界判断时,按需读取。

### 4.3 `docs/meta/claude_code_style_guide.md`

**来源**：`CLAUDE.md` 第 8 节(代码书写、注释与函数说明规则)

- 8.2 Python 函数 docstring 模板(Google-style)
- 8.3 注释边界(不堆砌无意义注释、优先注释复杂逻辑与边界判断)

**读取时机**：当任务涉及新增代码、新增公开函数或修改复杂逻辑时,按需读取。

### 4.4 `docs/meta/claude_reporting_guide.md`

**来源**：`CLAUDE.md` 第 10 节(测试、汇报与停止规则)

**内容**：
- 10.1 测试与完成表述规范(未验证前的措辞要求)
- 10.2 `/TODO.md` 与停止汇报的关系
- 10.3 每轮停止交接模板(7 个表格的完整结构)
- 10.4 下一条指令建议细则(8 种优先级场景与对应建议指令)

**读取时机**：当任务完成需要输出停止汇报、更新 `/TODO.md` 或建议下一条指令时,按需读取。

4. 验证 `CLAUDE.md` 索引可正常指向

## 7. 规格自检

- **占位符扫描**：无"待定"、"TODO"、未完成章节
- **内部一致性**：4 个细则文件覆盖用户明确列出的所有低频内容;CLAUDE.md 保留内容均为高频硬规则;索引指向正确
- **范围检查**：本设计只涉及文档拆分,不改变任何规则含义,范围可控
- **模糊性检查**：各细则文件的主题边界清晰,无重叠或遗漏
