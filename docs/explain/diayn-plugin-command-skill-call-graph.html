DIAYN Claude Code Plugin Runtime Map

Commands、Workflow Skills、Dependency Skills 到底怎么连起来

这页只解释当前 DIAYN Claude Code plugin 的调用逻辑：为什么 slash 菜单里同时有 /diayn:init 和 /diayn-init，以及 12 条 /diayn:* commands 如何按需路由到第三方 agent-skills。

不是这样

/diayn:init → /diayn-init

/diayn:init 不应该理解成在用户界面里再执行一次裸 slash 命令 /diayn-init。

实际是这样

command → workflow skill → router → dependency skills

/diayn:init 加载 command adapter，然后进入底层 DIAYN workflow skill； 需要第三方工程方法时，再 native 调用 dependency skills。

当前看到的现象

source: diayn
User slash menu
/diayn:init plugin command 推荐主入口
/diayn-init user-invocable workflow skill 当前也可见
/diayn:frontend plugin command 推荐主入口
/diayn-frontend user-invocable workflow skill 当前也可见
为什么都显示 diayn？

因为两者都可能来自 DIAYN plugin，不一定是 project-local fallback。

问题在哪里？

不是 skills 不该安装，而是用户可见入口没有分层隐藏好。

两套入口 主调用链 12 命令路由 安装方式 修复方向 第三方 skill 池

1. 两个入口来自两种不同 surface

/diayn:init 和 /diayn-init 背后可以进入相近的 DIAYN init 能力， 但入口来源不同：一个来自 plugin command，一个来自 plugin-visible workflow skill。

Plugin command path

/diayn:init 是 Claude plugin 推荐主入口

1

用户输入 /diayn:init

Claude Code 识别这是 DIAYN plugin 的 command。

2

加载 .claude/commands/init.md

command adapter 确认平台、入口文件和 DIAYN 命令身份。

3

进入 diayn:diayn-init workflow skill

这是 native skill 能力调用，不是再触发用户可见的 /diayn-init。

Workflow skill path

/diayn-init 是 workflow skill 的用户可见入口

1

用户输入 /diayn-init

Claude Code 直接把它当作可调用 skill 入口。

2

加载 skills/diayn-init/SKILL.md

直接按 skill 说明执行 DIAYN init workflow。

3

它不是 plugin 官方推荐主入口

plugin 场景中，理想状态是让 workflow skills 后台可调用，而不是作为用户主入口展示。

结论：现在同时出现两套入口，是因为 DIAYN plugin 同时暴露了 plugin commands 和 user-invocable workflow skills。 这叫“入口可见性没收敛好”，不是“dependency skills 污染”，也不是“应该删除 skills”。

2. 推荐主入口的完整调用链

这条链路解释了用户输入 /diayn:init 后，DIAYN 如何保持主控权，并在需要时才路由到第三方 skills。

command workflow skill dependency skills project docs
1
User command slash menu
/diayn:init、/diayn:backend、/diayn:review-frontend 等 12 条 plugin commands。
2
Command adapter .claude/commands/*.md
确认当前是 Claude Code plugin 场景，加载对应 adapter，例如 .claude/commands/init.md。
3
DIAYN workflow skill diayn:diayn-*
进入底层 workflow skill，例如 diayn:diayn-init。这里才是真正的 DIAYN command 业务逻辑。
4
DIAYN guardrails role / lane / state
确认角色、lane、worktree、写入范围、TODO 状态、OwnerGate、review/integration 边界。第三方 skills 不能覆盖这些规则。
5
Skill Router smallest useful set
读取 .diayn/dependency-routing/upstream-routing-map.md 或包内 routing map，只选择当前任务真正需要的第三方 skills。
6
Native skill call agent-skills dependency
Claude plugin 场景下按需调用 diayn:<dependency-skill>。直接读 vendored SKILL.md 只能算 fallback/reference。
7
Durable outputs project harness
生成或更新 CLAUDE.md、TODO.md、.diayn/*、docs/project/*、review log、integration summary 或 Owner-facing HTML。

4. 三种安装方式要分清

同一套 DIAYN workflow 语义，在不同平台/安装方式下暴露的用户入口不同。

Claude Code plugin / marketplace

官方主入口：/diayn:*

  • 用户推荐使用 /diayn:init、/diayn:plan、/diayn:backend。
  • 背后仍安装 DIAYN workflow skills 和 dependency skills。
  • 生成入口文件：CLAUDE.md。
Claude project-local fallback

本地短命令：/diayn-*

  • 用于不走 plugin / marketplace 的项目内安装。
  • 用户可以使用 /diayn-init、/diayn-plan。
  • 不要因为修 plugin 而破坏 fallback。
Codex / OpenCode adapter

按平台能力适配

  • 目标仍是同一套 12 条 DIAYN 命令体系。
  • 生成入口文件：AGENTS.md。
  • 平台不支持时不硬造假入口。

5. 当前问题与正确修复方向

修复目标是“收敛用户入口”，不是“删除能力”。

当前问题

commands + skills 同时用户可见

  • /diayn:* 和 /diayn-* 同时出现在用户 slash 菜单。
  • 用户不知道哪个才是 DIAYN plugin 推荐主入口。
  • 如果重复注册，还会出现大量重复项。
错误修复

不要把 plugin 改成 command-only

  • 不要删除 workflow skills。
  • 不要把 dependency skills 降级成纯文本参考。
  • 不要设置 disable-model-invocation:true。
  • 不要说 Skills 为空才正确。
正确修复

隐藏用户入口，保留后台调用

  • Claude plugin 用户主入口收敛到 12 个 /diayn:* commands。
  • plugin workflow skills 设置 user-invocable:false。
  • workflow/dependency skills 继续随 plugin 安装并可 native 调用。
  • project-local fallback 继续保留裸 /diayn-*。

6. 第三方 dependency skills 池

DIAYN 管理的是锁定版本的 agent-skills 依赖副本。DIAYN workflow 根据 routing map 按需选择，不允许第三方 skill 覆盖 DIAYN 的 role、lane、state、permission、review、integration 和 Owner authority。
