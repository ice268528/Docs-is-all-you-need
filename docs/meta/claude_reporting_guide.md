# Claude Code 汇报与停止细则

> 本文件定义测试表述规范、停止交接模板与下一条指令建议细则。
> 读取时机：当任务完成需要输出停止汇报、更新 /TODO.md 或建议下一条指令时，按需读取。

## 1. 测试、汇报与停止规则

### 1.1 测试与完成表述

- 未验证前，不应说“已经修好”或“已经完成”。应说“已修改，尚未验证”或“已完成实现，待验证”。
- 验证优先级：直接相关测试 > 回归测试 > 构建 / 类型检查 / lint / 运行验证 > 手动测试说明整理。
- 若环境、权限或依赖不足，应明确说明：已做哪些验证、未做哪些验证、未做原因、yiyi 还需要补做什么。
- 每次完成一轮有实际动作的任务后，必须优先汇报：任务主线、主线是否完成、这次完成了什么、改了哪些文件、如何验证、`/TODO.md` 是否已同步、是否需要 yiyi 检查/决策/补充，以及建议 yiyi 下一条发出的指令。
- 不要为了写停止汇报而读取所有项目文档。停止汇报应基于本轮已经读取和修改的文件、已执行的命令、已更新的 `/TODO.md` 状态，以及明确缺失的上下文。若需要额外上下文才能判断下一步，应在“需要 yiyi 决策或补充的内容”中说明需要 yiyi 提供什么，而不是自行扩大读取范围。
- 在以下情况，Claude Code 完成当前明确任务后应停止并等待 yiyi 下一步指令：下一步会改变阶段边界；下一步会修改只读文档或询问后可改文档但尚未获得确认；下一步未被本文件授权为自动衍生动作；继续执行将依赖猜测；存在不清楚之处需要 yiyi 进一步确认；发现的是新的独立 Bug、跨阶段问题或边界变化，而不是当前任务直接相关问题；测试或验收仍未完成，但是否继续推进需要 yiyi 决策。

### 1.2 `/TODO.md` 与停止汇报的关系

- `/TODO.md` 是当前阶段剩余任务、待测项、待验收项、阻塞项的权威来源。
- 停止汇报不应替代 `/TODO.md`，也不应把 `/TODO.md` 的全部内容重复复制到聊天输出。
- 停止汇报只需要说明：本轮是否已更新 `/TODO.md`；哪些新增/变更状态值得 yiyi 注意；如果没有更新，为什么不需要更新。
- 如果 Claude Code 无法判断当前阶段是否完成，应说明“无法判断”的原因，并告诉 yiyi 需要提供或确认哪个文档、哪个 TODO 项或哪个验收结果。
- 若下一步需要更多上下文，优先向 yiyi 说明需要补充什么上下文；不要为了猜测下一步而主动把所有文档塞进上下文。

每次任务停止并向 yiyi 输出时，必须使用以下结构。标题必须写清楚本轮任务主线，也就是这轮工作的“大目标”。

````markdown
建议 yiyi 下一条发送：

```text
````

### 1.4 下一条指令建议规则

Claude Code 在停止汇报中必须根据当前状态给出一条最合适的下一步指令建议。建议应可直接复制发送，且不得含糊。

优先级如下：

1. **存在缺失信息、关键决策或模糊需求**：建议 yiyi 补充信息或选择方案。

   ```text
   请根据上面的“需要 yiyi 决策或补充的内容”确认方案，然后继续实现。
   ```

2. **实现已完成但验证不足**：建议 yiyi 发出测试指令。

   ```text
   请测试这次实现是否有误，并整理测试结果。
   ```

3. **完成了一个业务需求，但缺少手动业务验收流程**：建议建立手动业务测试文档。

   ```text
   请建立这个业务需求的手动业务测试文档。
   ```

4. **当前阶段主要功能已完成，直接相关验证通过，且没有明显阻塞**：建议提交 commit。

   ```text
   请检查本轮改动，确认无误后提交 commit。
   ```

5. **commit 已完成**：建议进入代码优化。

   ```text
   请完善代码，对代码进行优化。
   ```

6. **代码优化已完成但尚未充分测试**：建议测试优化后的代码。

   ```text
   请测试完善后的代码是否有误，并整理测试结果。
   ```

7. **代码、测试、业务验收文档和阶段收尾均已满足，适合进入下一阶段**：建议创建下一阶段文档。

   ```text
   请创建下一阶段的文档。
   ```

8. **当前任务未完成但下一步明确**：建议继续当前任务。

   ```text
   请按 `/TODO.md` 中当前阶段的下一项继续执行，并在完成后按 CLAUDE.md 的停止交接模板汇报。
   ```
