# Agent 代码书写细则

> 本文件定义 Code Agent 在目标项目中新增或修改代码时的通用风格边界。

## 1. 总原则

- 先理解现有代码，再修改。
- 优先沿用项目已有框架、目录结构、命名和 helper API。
- 做解决当前问题所需的最小改动。
- 不添加未要求的功能、抽象、配置、依赖或未来假设。
- 不顺手重构无关代码。
- 不用猜测补全业务事实。

## 2. 注释与文档字符串

### 2.1 何时写注释

只在以下情况写注释：

- 代码意图不容易从实现本身看出。
- 存在重要业务约束、兼容性约束或安全边界。
- 复杂算法、状态机、并发逻辑或错误恢复需要提示读者。

### 2.2 何时不写注释

不要写解释语法或重复代码表面的注释，例如：

- “设置变量”
- “调用函数”
- “返回结果”

### 2.3 docstring 建议

公共函数、复杂 helper 或跨模块 API 可写简短 docstring，说明：

- 输入是什么。
- 输出是什么。
- 关键副作用或异常条件是什么。

## 3. 依赖与抽象

- 新依赖必须符合 `docs/project/implementation_constraints.md`。
- 单次使用逻辑不应过早抽象。
- 只有当抽象能明显减少重复、降低复杂度或匹配现有模式时才引入。

## 4. 测试配套

- Bug 修复应优先补充能覆盖复现路径的测试。
- 新功能测试范围应匹配风险和影响面。
- 重构应证明行为前后一致。
- 如果无法自动验证，必须整理手动验证口径并说明风险。

## 5. 修改边界

每一处改动都应能追溯到当前任务。若发现无关问题：

- 可以在汇报中说明。
- 可以建议创建 TODO、REQ 或 BUG。
- 不主动修改，除非它阻塞当前任务且修复范围直接相关。
