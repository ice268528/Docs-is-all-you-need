# Claude Code Alpha Package

DDDV8 currently has two Claude Code package shapes:

```text
plugins/docs-is-all-you-need/
packages/claude-project-local/
```

## Plugin Package

Relevant plugin files:

```text
.claude-plugin/plugin.json
.claude-plugin/marketplace.json
.claude/commands/diayn-*.md
skills/diayn-*/
dependency-skills/
```

The 12 Claude plugin command files are thin entry points. In plugin-dir mode they invoke namespaced workflow skills:

```text
/docs-is-all-you-need:diayn-init -> docs-is-all-you-need:diayn-init
...
/docs-is-all-you-need:diayn-html -> docs-is-all-you-need:diayn-html
```

Validation performed:

```text
claude plugin validate plugins\docs-is-all-you-need
node maintainers\scripts\validate_diayn_alpha_package.js --json validation\phase4_alpha_package.json
```

Result: the Claude plugin manifest validates, and the local package validator confirms 12 commands, 12 public skills, and the dependency payload.

Phase 9 plugin-dir probe:

- `claude --plugin-dir plugins\docs-is-all-you-need ... /docs-is-all-you-need:diayn-init` loads namespaced commands/skills and triggers the native `Skill` tool for `docs-is-all-you-need:diayn-init`.
- `claude --bare --plugin-dir plugins\docs-is-all-you-need ... /diayn-init` returns `Unknown command: /diayn-init`.

Conclusion: plugin-dir mode is valid for namespaced Claude plugin behavior, but it is not the bare `/diayn-*` user-facing path.

## Project-Local Package

The project-local package is generated by:

```text
node maintainers\scripts\build_claude_project_local_package.js
```

Relevant package files:

```text
packages/claude-project-local/.claude/commands/diayn-*.md
packages/claude-project-local/.claude/skills/diayn-*/
packages/claude-project-local/.claude/skills/<agent-skills-name>/
packages/claude-project-local/.diayn/dependency-routing/upstream-routing-map.md
packages/claude-project-local/.diayn/internal-role-skills/
packages/claude-project-local/diayn-package.json
```

The project-local package keeps the public command surface to 12 bare `/diayn-*` commands. It also exposes the locked `agent-skills` dependency copy as project-local skills so Claude can load them through the native `Skill` tool.

Validation performed:

```text
node maintainers\scripts\validate_diayn_claude_project_local_package.js --json validation\phase9_claude_project_local_package.json
```

Runtime probes recorded in `validation/phase9_claude_project_local_probe.json`:

- bare `/diayn-init` triggered the native `Skill` tool with `skill: "diayn-init"`;
- direct dependency probe triggered the native `Skill` tool with `skill: "idea-refine"`.

Routed dependency probe recorded in `validation/phase9_claude_project_local_routed_dependency_probe.json`:

- bare `/diayn-init` triggered the native `Skill` tool with `skill: "diayn-init"`;
- the active DIAYN init workflow treated the task as a vague idea requiring idea refinement;
- dependency routing triggered the native `Skill` tool with `skill: "idea-refine"`.

Command sequence probe recorded in `validation/phase9_claude_project_local_command_sequence.json`:

- all 12 bare `diayn-*` commands were visible in Claude init payloads;
- all 12 workflow skills were visible in Claude init payloads;
- all 12 bare `/diayn-*` commands entered workflow context;
- validation short-circuit arguments are not reliable evidence because normal workflow startup may run before the requested identity echo.

Conclusion: Claude Code CLI has a proven project-local alpha surface for bare
`/diayn-*` discovery, 12-command workflow entry, routed dependency-skill smoke
validation, and the complete installed-flow fixture through Owner acceptance,
closeout, and next-stage baseline refresh. This is still not a broad release or
all-surface claim because Codex Desktop runtime discovery/invocation remains
blocked and OpenCode is deferred.
